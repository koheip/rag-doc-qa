# RAG の評価ガイド（初心者向け）

「なんとなく良さそう」ではなく、**数字で測って、改善したことを数字で示す** ための仕組みです。
このドキュメントでは、評価で使っている指標の意味・採点の方法・費用の計算方法・実行方法を説明し、
最後に面接で聞かれそうな質問と回答例をまとめます。

---

## 1. 何を測っているのか（全体像）

RAG は「検索」と「生成」の2段階なので、評価も2段階に分けます。分けて測ることで、
**うまくいかないときに、どちらが原因か** を切り分けられます。

| 段階 | 何を見るか | 指標 | API キー |
| --- | --- | --- | --- |
| ① 検索 | 正解が書かれたチャンクを取ってこられたか | Hit@1, Hit@3, Recall@k, MRR | 不要（無料） |
| ② 生成 | 取ってきた資料から正しく答えられたか | 正答率（LLM 採点）, 拒否の正しさ | 必要 |
| ③ 運用 | お金と時間がどれだけかかるか | トークン数, 費用, 応答時間 p50/p95 | 必要 |

## 2. 評価データセット（`eval/questions.jsonl`）

サンプル PDF（架空の会社の就業規則・FAQ、11ページ）に対する 30 問です。1行が1問の JSON Lines 形式です。

```json
{"id": "q02", "type": "paraphrase", "question": "給料日はいつですか？",
 "evidence": [{"page": 3, "keyword": "翌月25日に従業員指定"}],
 "reference_answer": "毎月末日締め・翌月25日払い。25日が銀行休業日の場合は前営業日に支払われる。"}
```

- `evidence`（根拠）: 正解が書かれている場所。「ページ番号」と「その箇所に含まれるキーワード」の組です。
  チャンクの区切り方（チャンクサイズ）を変えても使えるよう、チャンク番号ではなくキーワードで指定しています。
  **ページが一致し、かつキーワードを含むチャンク** を「関連チャンク」とみなします。
- `reference_answer`: 模範解答。LLM による採点で使います。
- `type`（質問の種類）:

| type | 問数 | 内容 | 例 |
| --- | ---: | --- | --- |
| fact | 10 | 資料の言葉そのままで聞く | 人事評価は何段階？ |
| paraphrase | 13 | 資料と違う言葉で聞く（言い換え） | 「給料」日（資料は「給与」）、「ボーナス」（資料は「賞与」）、「在宅勤務」（資料は「リモートワーク」） |
| reasoning | 2 | 資料から一歩考えて答える | 新幹線のグリーン車に乗っていい？（資料は「普通車指定席」） |
| multi | 1 | 2か所の情報を組み合わせる | 結婚したら何日休めて、お祝い金はいくら？ |
| unanswerable | 4 | 資料に答えが無い | 退職金はいくら？（「退職」の話題はあるが金額の記載は無い） |

データセットを作るときに気をつけたこと:
- **今のシステムが得意な質問だけにしない**。言い換え質問を多めにし、「出張申請の期限（5営業日前）」と
  「有給申請の期限（3営業日前）」のように、似た記述が複数ある紛らわしい質問も入れています。
- 回答不能な質問には、資料の話題に近いもの（有給の買い取り、退職金）も入れ、「それっぽい資料があっても推測しないか」を見ます。
- `run_eval.py` は実行時に、すべての `evidence` が実際にどこかのチャンクに存在するかを確認します（書き間違いの検出）。

## 3. 検索の指標

検索結果（上位10件）の中で、**最初に関連チャンクが出てきた順位** を基本にします。

| 指標 | 意味 | 計算 | 例（正解が2位だった場合） |
| --- | --- | --- | --- |
| **Hit@1** | 1位が正解だった割合 | 1位が関連チャンクなら1、違えば0 の平均 | 0 |
| **Hit@3** | 上位3件に正解が入っていた割合 | 3位以内なら1 の平均 | 1 |
| **Recall@k** | 必要な根拠のうち、上位 k 件で拾えた割合 | 拾えた根拠数 ÷ 必要な根拠数 の平均 | 根拠が2つで1つだけ拾えたら 0.5 |
| **MRR** | 正解がどれだけ上にあるか | 1 ÷ 順位 の平均（見つからなければ0） | 1/2 = 0.5 |

- アプリは上位 k 件（デフォルト4件）を LLM に渡すので、**Recall@k が低いと、LLM がどれだけ賢くても答えられません**。
- Hit@1 や MRR は「正解がどれだけ上位にあるか」を表します。k を小さくして費用を下げたいときや、
  リランキングの効果を見るときに重要です。
- 回答不能な質問は「正解の場所」が無いので、検索の指標からは除外しています。

## 4. 生成の指標と LLM-as-a-judge

### なぜ LLM に採点させるのか
回答は「毎月25日です」「給与は翌月25日払いで、休日なら前営業日です」のように、正しくても言い回しが毎回変わります。
文字列の完全一致では正しく採点できず、人が30問×モデル数を毎回採点するのは大変です。
そこで、**別の LLM に「模範解答と比べて正しいか」を判定させる**（LLM-as-a-judge）方法を使います。

- 採点モデル: `gemini-3.1-flash-lite`（デフォルトの回答モデル `gemini-3.5-flash-lite` とは別のモデル。`--judge-model` で変更可）
  - 本当は回答モデルより賢いモデルで採点するのが理想です。しかし無料枠では、上位モデルの1日あたりの上限が小さく
    （2026-10-21 時点で `gemini-3.6-flash` は 20回/日）、30問の採点が終わらないため、上限に余裕のある軽量モデルを使っています。
    数値の照合が中心の採点なので軽量モデルでも大きな問題は少ないですが、限界の1つとして理解しておきます。
- 採点は **0/1 の2値**。採点基準（`eval/judge.py` の `JUDGE_SYSTEM_PROMPT`）:
  - 1: 模範解答の要点（数値・期限・可否など）を正しく含み、誤った情報が無い。言い回しの違いや正しい補足は減点しない
  - 0: 要点が欠けている・数値が違う・誤りを含む・「わからない」と答えた
- `temperature=0` と JSON 出力（`{"score": 1, "rationale": "理由"}`）で、なるべく毎回同じ判定になるようにしています。
  理由（rationale）も残すので、不正解の原因を後から確認できます。

### 生成の指標
| 指標 | 意味 |
| --- | --- |
| 正答率（回答可能） | 答えが資料にある 26 問のうち、採点で正解だった割合 |
| 誤って拒否 | 答えが資料にあるのに「わからない」と答えた割合（慎重すぎる） |
| 正しく拒否（回答不能） | 答えが資料に無い 4 問で、ちゃんと「わからない」と答えた割合（低いとハルシネーション） |
| 全体正答率 | 30 問すべてで正しく振る舞えた割合 |

拒否の判定は LLM ではなく、アプリと同じ `is_unknown()`（回答が「わからない」だけかどうか）で行います。

### LLM-as-a-judge の限界（必ず理解しておくこと）
- **採点モデルも間違える**。特に「部分的に正しい」回答の扱いはぶれやすい。不正解とされた回答は理由を読んで人が確認する。
- **自分（同じモデル系列）の回答を甘く採点する傾向** が知られている（自己選好バイアス）。回答モデルと採点モデルを分けるのはそのため。
  モデル比較で `gemini-3.1-flash-lite` 自身の回答も `gemini-3.1-flash-lite` が採点しているので、その行は割り引いて見る必要がある。
- 2値採点は分かりやすい反面、「惜しい回答」と「全く違う回答」を区別できない。より細かく見たいなら 1〜5 点の採点や、
  RAGAS のように「忠実性（Faithfulness）」「回答の関連性」などに分けて測る方法がある。
- 30 問は少ないので、1問の差で約 3〜4 ポイント変わる。**小さな差は誤差の範囲** として扱う。

## 5. 費用と速度

- トークン数: Gemini の応答に含まれる `usage_metadata` から取得します。
  - 入力 = `prompt_token_count`（システムプロンプト＋参考資料＋質問）
  - 出力 = `candidates_token_count` ＋ `thoughts_token_count`（モデルが内部で考えた「思考」トークンも出力料金で課金されるため）
- 費用 = 入力トークン × 入力単価 ＋ 出力トークン × 出力単価（単価は 100万トークンあたりの USD）
  - 単価は `eval/pricing.py` に、出典 URL と確認日付きで定数として書いています（https://ai.google.dev/gemini-api/docs/pricing 、2026-10-21 確認）。
  - 無料枠（Free Tier）では $0 ですが、**本番で有料枠を使った場合の目安** として有料枠の単価で換算した値も表示します。
  - 採点（judge）の費用は「システムを動かす費用」ではないので、表には含めていません。
- 応答時間: 回答生成の API 呼び出し1回にかかった時間。**p50（中央値）** は「普通の速さ」、
  **p95** は「遅いときの速さ（20回に1回はこれより遅い）」を表します。平均だと、たまに極端に遅い回があると引っ張られるため、パーセンタイルで見ます。
- 無料枠のレート制限対策: 呼び出しの間に `--sleep` 秒（デフォルト4秒）待ち、429（回数超過）や 503（混雑）のときは
  10秒→20秒→40秒…と待ち時間を倍にして再試行します（指数バックオフ）。
  ただし「1日の上限に達した」429 はサーバーが「約24時間後に再試行」と返すので、待たずにそのモデルの評価を打ち切ります。
  1問ずつの採点に失敗した場合は、その問を正答率の計算から除外し、レポートに件数を表示します。

## 6. 実行方法

```bash
# 検索精度だけ（API キー不要・数十秒）
python eval/run_eval.py --skip-generation

# チャンクサイズの比較（検索のみ）
python eval/run_eval.py --skip-generation --chunk-sizes 150 200 300 400

# 検索＋生成＋採点（GEMINI_API_KEY が必要。無料枠だと数分〜十数分）
python eval/run_eval.py

# モデル比較
python eval/run_eval.py --models gemini-3.5-flash-lite gemini-3.1-flash-lite gemini-3.8-flash

# BM25 ハイブリッド検索を実装したら（src/bm25.py の課題）
python eval/run_eval.py --skip-generation --retrievers dense hybrid
```

結果は `eval/results/<日時>.md`（表）と `eval/results/<日時>.json`（全質問の回答・採点理由・トークン数など）に保存されます。
生成の評価は API 呼び出しを減らすため、**最初に指定した検索方式・チャンクサイズの組み合わせだけ** で行います。

## 7. 改善のサイクル

1. ベースラインを測る（今の数字を記録）
2. 不正解・取りこぼした質問を見て、原因が「検索」か「生成」かを切り分ける
3. 1つだけ変える（例: チャンクサイズ、検索方式、プロンプト、モデル）
4. 同じデータセットで測り直し、数字で比べる
5. 良くなったら採用、悪くなったら原因を考える（**悪くなることも普通にある**）

## 8. 今回の結果の読み方（2026-10-21 のベースライン）

結果の表は README の「評価」セクションにあります。ポイントは次の3つです。

- 検索は Hit@3 = 96% と高い一方、Hit@1 = 73% で「正解が 2〜4 位に来る」ことが多い → 次の改善の的は 1 位の精度。
- 回答品質は 2 モデルとも 30/30 で **上限に張り付いている**（天井効果）。このデータセットでは、モデルの差は費用と速度にしか出ない。
  モデルの差を見たいなら、より難しい質問（複数箇所をまたぐ・計算が必要など）を追加する必要がある。
- 改善を数字で示すなら、今は **検索の Hit@1・MRR** が一番わかりやすい指標。

## 面接での想定質問と回答例

**Q1. RAG の精度をどうやって測りましたか？**
A. 検索と生成を分けて測りました。検索は、30問の評価データに正解の根拠（ページとキーワード）を付けておき、
Hit@k・Recall@k・MRR を計算しています。生成は、模範解答と比べて正しいかを別の LLM に採点させる LLM-as-a-judge で正答率を出し、
資料に答えが無い質問で「わからない」と答えられたかも測っています。さらにトークン数から費用、API の応答時間から p50/p95 も記録しています。

**Q2. なぜ検索と生成を分けて評価するのですか？**
A. 回答が間違ったとき、原因が「正しい資料を取ってこられなかった」のか「資料はあったのに LLM が読み違えた」のかで、
直すべき場所が全く違うからです。前者ならチャンク分割や検索方式、後者ならプロンプトやモデルを見直します。

**Q3. Hit@k と MRR の違いは？**
A. Hit@k は「上位 k 件に入ったかどうか」の0/1なので、3位でも1位でも同じ扱いです。MRR は 1/順位 の平均なので、
正解がより上位にあるほど高くなります。LLM に渡す件数を減らしたい（費用削減）ときは、MRR や Hit@1 が重要になります。

**Q4. LLM-as-a-judge は信用できるのですか？**
A. 完全には信用できません。採点モデルも間違えますし、自分と同じモデルの回答を甘く採点する傾向もあります。
そこで、回答モデルと採点モデルを分ける、temperature を0にする、採点理由を出力させて不正解は人が確認する、といった対策をしています。
本格的にやるなら、一部を人手で採点して LLM の採点との一致率を確認するべきだと考えています。

**Q5. 評価データはどうやって作りましたか？偏りは？**
A. 自分で30問作りました。今のシステムに有利にならないよう、資料と違う言葉で聞く言い換え質問を半分近く入れ、
似た記述が複数ある紛らわしい質問や、話題は近いが答えが無い質問も入れています。ただし、作った本人が作った質問なので偏りは残ります。
実際の利用ログから質問を集めるのが理想です。

**Q6. チャンクサイズはどう決めましたか？**
A. 150・200・300・400文字で検索精度を比較しました。結果は README の表の通りで、200文字が最もバランスが良かったため採用しています。
300文字では言い換え質問の Hit@3 が大きく下がりました。1つのチャンクに複数の話題が混ざって、ベクトルの意味がぼやけたためだと考えています。

**Q7. 費用はどう見積もりましたか？**
A. API の応答に含まれるトークン数（入力・出力・思考トークン）に、公式の料金表の単価を掛けて計算しています。
単価は出典 URL と確認日付きでコードに定数として書いています。無料枠では $0 ですが、有料枠に換算した1000問あたりの費用も出しています。

**Q8. 応答時間を平均ではなく p50/p95 で見るのはなぜ？**
A. 平均は、たまに起きる極端に遅い応答に引っ張られるからです。ユーザー体験では「普段どれくらいか（p50）」と
「遅いときどれくらいか（p95）」の方が重要です。

**Q9. 正答率が 100% でしたが、評価として意味はありますか？**
A. 回答の正答率は上限に張り付いていて、モデルの差を測る力は弱いです（天井効果）。そのことは結果と一緒に明記しています。
一方で、検索の Hit@1 は 73% で改善の余地がはっきり見えていますし、費用（1000問あたり $0.19〜$0.25）や応答時間の差も測れています。
次は難しい質問を追加して、回答側でも差が出るデータセットにしたいと考えています。

**Q10. 次に何を改善しますか？**
A. BM25 を使ったハイブリッド検索を実装し、同じ評価データで dense 単体と比較します。日本語は文字 n-gram でトークン化し、
ベクトル検索の結果と RRF で統合する予定です。言い換えに強いベクトル検索と、数字や固有名詞の一致に強い BM25 を組み合わせることで、
Hit@1 の改善を狙います。ただし、効果があるかどうかは測ってみるまでわからないので、必ず数字で確認します。

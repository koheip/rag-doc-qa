# コード解説と想定質問集

このドキュメントは、本アプリのコードを **初めて読む人向け** に、各ファイルが何をしているかを順番に説明したものです。
後半には、面接で聞かれそうな質問と回答例をまとめています。

---

## 0. まず全体像

RAG（検索拡張生成）は次の2段階でできています。

```
【準備】PDF → テキスト → チャンク → ベクトル → ベクトルストアに保存
【質問】質問 → ベクトル → 似ているチャンクを検索 → チャンク＋質問を LLM に渡す → 回答
```

LLM は学習していない情報（社内規則など）を知りません。そこで「質問に関係しそうな部分を先に探して、
カンニングペーパーとして渡す」のが RAG の考え方です。

ファイルとの対応:

| 段階 | ファイル | ひとことで |
| --- | --- | --- |
| 読み込み | `src/loader.py` | PDF をページごとの文字列にする |
| 分割 | `src/chunker.py` | 長い文字列を約200文字のかたまりにする |
| ベクトル化 | `src/embedder.py` | 文字列を「意味を表す数値の並び」にする |
| 保存・検索 | `src/vector_store.py` | 数値の並びを保存し、似ているものを探す |
| 検索器 | `src/retriever.py` | 上の2つをまとめて「質問→関連チャンク」を1行で呼べるようにする（検索方式は差し替え可能） |
| 課題 | `src/bm25.py` | BM25 ハイブリッド検索（未実装の課題） |
| 生成 | `src/llm.py` | 関連チャンクを根拠に LLM で回答を作る |
| LLM 呼び出し | `src/llm_client.py` | Gemini などの LLM を呼ぶ部分（提供元を差し替え可能） |
| 画面 | `app.py` | Streamlit で全部をつなぐ |
| 設定 | `src/config.py` | モデル名やデフォルト値を1か所にまとめる |

---

## 1. `src/loader.py` — PDF の読み込み

- `load_pdf()` は pypdf の `PdfReader` で PDF を開き、`page.extract_text()` で1ページずつ文字を取り出します。
- 結果は `Page(source=ファイル名, page=ページ番号, text=本文)` という **dataclass** で返します。
  ページ番号を持たせておくのは、最後に「p.3 に書いてあります」と出典を表示するためです。
- `clean_text()` は PDF 特有の問題を直します。PDF は「見た目の行」で改行が入るので、
  「申\n請する」のように文の途中で改行が入ります。そこで **文末（。など）以外の改行は削除** して文をつなげます。
  また「- 2 / 7 -」のようなページ番号だけの行も、検索のノイズになるので捨てます。
- 引数はパス・バイト列・ファイルオブジェクトのどれでも受け取れるので、Streamlit のアップロードにもそのまま使えます。

## 2. `src/chunker.py` — チャンク分割

**なぜ分割するのか？**
1ページまるごとだと複数の話題が混ざり、ベクトルの意味がぼやけて検索精度が下がります。
逆に短すぎると文脈が足りません。本アプリでは日本語 200 文字（規則1〜2条ぶん）をデフォルトにしています。

**日本語向けの工夫**
- 英語は単語数で区切れますが、日本語はスペースが無いので **文字数** で長さを測ります。
- 文の途中で切ると意味が壊れるので、`split_sentences()` で「。」「！」「？」・改行の位置で文に分けてから、
  `split_text()` で **文を順番に箱へ詰める** ように chunk_size まで入れていきます。
- **オーバーラップ**: 新しいチャンクを始めるとき、前のチャンクの最後の文（overlap 文字以内）を引き継ぎます。
  こうすると「答えがちょうどチャンクの境目にある」場合でも、どちらかのチャンクに文脈ごと入ります。
- 句点の無い極端に長い文は、文字数で強制的に切ります（スライディングウィンドウ）。
- `chunk_pages()` は **ページをまたがずに** 分割します。こうすると各チャンクのページ番号が1つに決まり、出典が正確になります。

## 3. `src/embedder.py` — 埋め込み（ベクトル化）

- **埋め込み** とは、文章を数百個の数字の並び（ベクトル）に変換することです。意味が近い文章ほど、ベクトルの向きが近くなります。
- `intfloat/multilingual-e5-small` は日本語を含む約100言語に対応した無料のモデルで、384次元のベクトルを出力します。
- E5 は学習時に「検索する側には `query: `、される側には `passage: `」を付けて学習しているので、使うときも同じ接頭辞を付けます。
  付け忘れると精度が下がります。
- `normalize_embeddings=True` でベクトルの長さを1にそろえます。長さ1どうしなら **内積 ＝ コサイン類似度** になり、計算が簡単になります。
- `Embedder` という **Protocol（インターフェース）** を定義しています。「`embed_documents` と `embed_query` を持っていれば何でもよい」
  という約束なので、テストでは偽物（FakeEmbedder）に差し替えられ、将来 OpenAI の埋め込み API などに替えるのも簡単です。

## 4. `src/vector_store.py` — ベクトルストア（FAISS）

- FAISS は Meta が作った「似ているベクトルを高速に探す」ライブラリです。
- `IndexFlatIP` は「全件と内積を計算して大きい順に返す」いちばん素直な方式です（Flat＝総当たり、IP＝内積）。
- `self.chunks` に、FAISS に入れたのと **同じ順番** でチャンクを保存しておきます。FAISS は「i 番目が近い」と番号だけ返すので、
  その番号で `self.chunks[i]` を引けば元の文章と出典が分かります。
- `search()` は `(チャンク, 類似度)` のリストを返します。top_k がチャンク数より大きくてもエラーにならないよう `min()` で調整しています。

## 5. `src/retriever.py` — 検索器

- `Retriever` は「`index(chunks)` と `retrieve(question, top_k)` を持つもの」という **インターフェース（Protocol）** です。
- 今の実装は `DenseRetriever`（埋め込みベクトルで意味の近さを測る検索）です。埋め込みモデルとベクトルストアを組み合わせています。
- `create_retriever("dense", embedder)` のように **戦略名で検索器を作る工場関数** を用意しています。
  アプリや評価スクリプトはこの関数だけを使うので、検索方法を追加しても呼び出し側は変わりません（**ストラテジーパターン**）。
- `"hybrid"`（BM25 ＋ ベクトル検索）は `src/bm25.py` の課題として未実装で、実装すると選べるようになります。
- 埋め込みモデルは外から渡す（**依存性の注入**）ので、テストでは FakeEmbedder を渡しています。

## 6. `src/llm.py` — 回答の生成

- `build_prompt()` は、検索したチャンクに `[1]` `[2]` と番号と出典を付けて並べ、最後に質問を付けます。
- `SYSTEM_PROMPT` で次のルールを与えています:
  1. 参考資料だけを根拠にする（自分の知識で補わない）
  2. 書かれていなければ「わからない」と答える
  3. 根拠にした資料の番号を付ける
  これにより、もっともらしい嘘（**ハルシネーション**）を減らし、回答の検証もしやすくなります。
- `generate_answer(question, contexts, llm)` はプロンプトを作って `llm.generate()` を呼びます。
  `temperature=0.1` と低めにして、毎回ぶれない・資料に忠実な回答にしています。
- LLM の呼び出し自体は `src/llm_client.py` に分けています。`LLMClient` というインターフェースと、その Gemini 版 `GeminiClient` があり、
  公式 SDK `google-genai` の `client.models.generate_content()` を呼びます。戻り値の `LLMResponse` には回答に加えて
  **入力・出力トークン数と応答時間** が入っていて、画面表示や評価（費用・速度の計測）に使います。
  Azure OpenAI などに対応するときは、同じ `generate()` を持つクラスを追加するだけです。
- `GeminiClient` は、429（回数制限）や 503（混雑）のとき待ち時間を倍にしながら再試行し（指数バックオフ）、
  タイムアウト（60秒）も設定しています。実際に評価を回したところ、混雑時に応答が返らず固まることがあったためです。
- `cited_indices()` は回答文から `[2]` のような番号を取り出します。画面の「出典」には、検索した全チャンクではなく
  **LLM が実際に根拠にした資料だけ** を表示するためです。
- `is_unknown()` は「わからない」だけの回答かを判定します。実際に試したところ、LLM が「わからない [1][2][3][4]」のように
  根拠が無いのに番号を付けてしまうことがあったので、その場合は表記を「わからない（資料に該当する記述が見つかりませんでした）」に
  そろえ、出典も「なし」と表示するようにしました（プロンプトでも「この場合は番号を付けない」と指示）。
- `extractive_answer()` は API キーが無いときの代わりの回答です。上位2件のチャンクをそのまま引用表示します。
  LLM を使わないので費用ゼロ・オフラインでも動きます（埋め込みモデルのダウンロード後）。

## 7. `app.py` — Streamlit 画面

- Streamlit は **操作のたびにスクリプト全体が上から再実行される** 仕組みです。そのため:
  - 重い埋め込みモデルは `@st.cache_resource` で1回だけ読み込みます。
  - 作ったインデックスやチャット履歴は `st.session_state` に入れて、再実行しても消えないようにします。
- API キーは「環境変数 → `st.secrets` → サイドバー入力」の順で探します。サイドバー入力は `type="password"` で伏せ字にし、どこにも保存しません。
- 質問が来たら、①`retriever.retrieve()` で検索 → ②キーがあれば `generate_answer()`、無ければ `extractive_answer()` → ③出典と検索結果を表示、の順に処理します。
- Gemini の呼び出しが失敗した場合（キー間違い・回数制限など）も、アプリを止めずに抽出モードの結果を表示します。

## 8. テスト（`tests/`）

- `test_chunker.py`: チャンクがサイズ上限を守るか、文を取りこぼさないか、オーバーラップが効いているか、などを確認。
- `test_retriever.py`: **FakeEmbedder**（文字の出現回数を数えるだけの偽の埋め込み）を使います。
  本物のモデル（約470MB）を読み込まないので、テスト全体が1秒未満で終わります。
  「同じ文字を多く含む文章が上位に来る」ので、検索の順位付け・top-k・エラー処理の確認には十分です。
- `test_llm.py`: API を呼ばない部分（プロンプトに出典が入っているか等）をテストします。`FakeLLM`（決まった文字列を返すだけの偽 LLM）を使います。
- `test_eval_metrics.py`: 評価指標（Hit@k・MRR など）や費用計算が正しいかのテスト。
- `test_bm25_exercise.py`: 課題用のテスト。`@pytest.mark.exercise` が付いていて、通常の `pytest` では実行されません（`pytest -m exercise` で実行）。

## 9. 評価（`eval/`）

精度・費用・速度を数字で測る仕組みです。詳しくは [EVAL.md](EVAL.md) を参照してください。

## 想定質問と回答例

### RAG・全体

**Q1. RAG とは何ですか？なぜ使うのですか？**
A. 質問に関係する文書を検索し、その内容を LLM に渡して回答させる手法です。LLM が学習していない社内文書や最新情報にも答えられ、
回答の根拠（出典）を示せるので検証しやすいのが利点です。ファインチューニングと比べて、文書を差し替えるだけで知識を更新できる点も大きいです。

**Q2. ファインチューニングとの違いは？**
A. ファインチューニングはモデルの重み自体を学習し直すので、コストが高く、情報を更新するたびに再学習が必要です。
RAG はモデルはそのままで、渡す資料を変えるだけです。「知識を足したい」なら RAG、「話し方や出力形式を変えたい」ならファインチューニングが向いています。

**Q3. このアプリでハルシネーションをどう抑えていますか？**
A. ①プロンプトで「資料だけを根拠に、無ければ『わからない』と答える」と指示、②temperature を 0.1 に下げる、
③出典番号を付けさせ、実際に参照された資料だけを出典として表示し、元のチャンクも確認できるようにする、の3点です。
実際に動かしたところ「わからない」なのに番号を付けてくることがあったので、その場合はコード側で表記をそろえて出典を出さないようにしました。完全には防げないので、利用者が根拠を確認できる UI にしています。

### チャンク分割

**Q4. チャンクサイズはどう決めましたか？**
A. 日本語200文字・オーバーラップ40文字をデフォルトにしました。サンプル PDF で 150/200/300 文字を比較したところ、
300文字では1チャンクに複数の条文が混ざって検索が外れることがあり、200文字前後が話題を1つに絞れてバランスが良かったためです。
ただし文書の種類で最適値は変わるので、サイドバーで変更できるようにしています。本来は評価データを作って数値で比較すべきです。

**Q5. オーバーラップはなぜ必要ですか？**
A. チャンクの境目に答えがあると、前半と後半が別々のチャンクに分かれて、どちらも単独では意味が通らなくなります。
少し重ねることで、どちらかのチャンクには文脈ごと含まれるようにしています。重ねすぎると重複が増えて無駄になるので、2割程度にしています。

**Q6. なぜページをまたいでチャンクを作らないのですか？**
A. 出典のページ番号を正確に1つに決めるためです。ページ境界で文が切れるデメリットはありますが、出典の正確さを優先しました。

### 埋め込み・検索

**Q7. なぜ multilingual-e5-small を選んだのですか？**
A. 無料でローカル実行でき、日本語に対応し、サイズが小さく CPU でも速いからです。API 型の埋め込みと違い、文書を外部に送らずにベクトル化できる点も利点です。
base 版とも比較しましたが、このサンプルでは精度に大きな差がなく、サイズが2倍以上になるため small にしました。

**Q8. `query:` と `passage:` は何のためですか？**
A. E5 は「質問」と「文書」を区別して学習されたモデルで、使うときも同じ接頭辞を付けるのが前提です。質問は短く、文書は長いという非対称性をモデルに伝える役割があります。

**Q9. コサイン類似度とは？なぜ内積で計算しているのですか？**
A. 2つのベクトルの「向き」がどれだけ近いかを -1〜1 で表したものです。ベクトルを長さ1に正規化しておけば、内積がそのままコサイン類似度になるので、
FAISS の内積インデックス（IndexFlatIP）で計算しています。

**Q10. FAISS と numpy、どちらでもよかったのでは？**
A. この規模なら numpy でも十分速いです。FAISS を選んだのは、実務で使われる定番ライブラリであることと、データが増えたときに
HNSW や IVF などの近似検索インデックスに1行で切り替えられる拡張性のためです。今の IndexFlatIP は総当たりなので、結果は numpy と同じく正確です。

**Q11. 類似度スコアにしきい値を設けていないのはなぜですか？**
A. E5 は無関係な文章どうしでも類似度が 0.8 前後になりやすく、関係あるものとの差が小さいため、固定のしきい値で切ると取りこぼしが出やすいからです。
そこで「関係があるかどうか」の最終判断は LLM に任せ、資料に無ければ「わからない」と答えさせています。改善策としてはリランカーの導入が考えられます。

**Q12. 検索精度をもっと上げるには？**
A. ①BM25 などのキーワード検索と組み合わせるハイブリッド検索（条文番号や固有名詞に強い）、②クロスエンコーダによるリランキング、
③チャンクの前に見出しを付けるなどの前処理、④質問の言い換え（クエリ拡張）などがあります。まず評価データを作り、Recall@k で効果を測ってから導入するのが良いと考えています。

### LLM・API

**Q13. なぜ Gemini を選んだのですか？モデルは何ですか？**
A. 無料枠があり、公式 SDK（google-genai）で簡単に呼べるからです。デフォルトは無料枠で使える `gemini-3.5-flash-lite` で、
高速・低コストなので RAG の回答生成のような「資料を要約して答える」タスクに向いています。モデル名は設定ファイルで変更できます。

**Q14. API キーの管理で気をつけたことは？**
A. コードには書かず、環境変数・`.env`・`st.secrets`・画面入力のいずれかで渡すようにし、`.env` と `secrets.toml` は `.gitignore` に入れています。
リポジトリには中身の無い `.env.example` だけを置いています。画面で入力したキーも保存しません。

**Q15. API キーが無い場合はどうなりますか？**
A. LLM を使わず、検索で見つかった上位のチャンクをそのまま回答として表示する「抽出モード」で動きます。費用ゼロで誰でも試せるようにするためです。
API 呼び出しが失敗したときも同じ表示にフォールバックします。

### 設計・テスト

**Q16. なぜモジュールを分けたのですか？**
A. 1つのファイルに全部書くと、どこを直せばよいか分かりにくく、部品の交換やテストも難しくなるからです。
例えば埋め込みモデルを替えたいときは `embedder.py` だけ、ベクトルストアを Chroma に替えたいときは `vector_store.py` だけを直せばよい構成にしています。
UI に依存しないので、FastAPI で API 化するときも `src/` をそのまま使えます。

**Q17. テストで本物のモデルを使わないのはなぜですか？**
A. 本物のモデルは読み込みに時間がかかり、ダウンロードも必要なので、テストが遅く不安定になります。
検索ロジック（順位付け・top-k・エラー処理）の確認にはモデルの賢さは不要なので、文字の出現回数で作る偽の埋め込みを使っています。
実際のモデルでの動作は `scripts/demo_pipeline.py` で別途確認しています。

**Q18. Streamlit で注意した点は？**
A. 操作のたびにスクリプト全体が再実行される仕組みなので、重いモデルは `st.cache_resource` で1回だけ読み込み、
インデックスと会話履歴は `st.session_state` に保存しています。

**Q19. 本番運用するなら何が足りませんか？**
A. ①インデックスの永続化（今はメモリ上だけ）、②複数ユーザー対応とアクセス制御、③評価（RAGAS 等）による品質の数値化と監視、
④スキャン PDF 向けの OCR、⑤API 化（FastAPI）とフロントエンドの分離、⑥企業向けには Azure OpenAI や Bedrock などデータ管理がしやすい LLM 基盤への対応、などです。

**Q20. 一番苦労した点・工夫した点は？**（自分の言葉で答えられるように準備）
A. 例: 日本語のチャンク分割です。英語向けの分割方法をそのまま使うと文の途中で切れてしまうため、文字数と句点を基準にした分割を自作しました。
また PDF から取り出したテキストに不要な改行が入る問題があり、文末以外の改行を取り除く前処理を入れました。チャンクサイズは実際に比較して決めました。
